The ubuntu-service Family

A dedicated family of decoupled packages built exclusively for atomic, folder-contextual single-service operations on Ubuntu VPS servers.

1 Target Atomic Single Service
0 Memory No Standing Daemons

🎯 Explicit Family Scope: Singular (ubuntu-service), NOT Plural

ubuntu-service is built strictly around the single-service paradigm: you stand inside an application directory after git pull, and you need to identify, inspect, and restart that single service.

This family does not touch or conflate with whole-machine fleet inventory scanners (like ubuntu-services). Fleet management and server-wide folder auditing is an entirely separate operational domain with its own dedicated architecture.

The Decoupled Triad

The ubuntu-service family originated from a monolithic script that handled everything—parsing systemd INI files, matching directories, executing systemctl restart, polling status, and streaming journalctl logs.

To prevent silent restart failures and allow developers to embed detection or restart capabilities into other tooling without side-effects, the single-service lifecycle was decoupled into three focused repositories plus this dedicated documentation hub.

Interaction Workflow

How the Family Coordinates During Deployment

Here is the exact lifecycle sequence when a developer stands in a project folder and runs a single command:

1. Invocation (ubuntu-service)

You run us restart in /root/KeshavSoft/appointment-notifier. The orchestrator captures process.cwd() and initializes the workflow.

2. Detection (ubuntu-service-detect)

Scans /etc/systemd/system/. Scores matching unit files by WorkingDirectory (100) or ExecStart (70). Extracts port 3000. Zero modifications made.

3. Execution (ubuntu-service-restart)

Runs systemctl restart appointment.service. Verifies is-active health status, and streams live journalctl logs. Clean exit.
